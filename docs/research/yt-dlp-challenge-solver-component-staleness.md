Accessed: 2026-08-21

## Findings

1. **Kanıtlanmış platform gerçeği:** `--no-remote` and `--no-remote-components` are two different flags at two different layers, and the node only controls the second one. `--no-remote` is a **Deno** CLI flag, hardcoded by yt-dlp itself in `DenoJCP._DENO_BASE_OPTIONS = ['--ext=js', '--no-code-cache', '--no-prompt', '--no-remote', '--no-lock', '--node-modules-dir=none', '--no-config']`; the node neither passes it nor can suppress it. What the node passes is yt-dlp's own `--no-remote-components`. Sources: [`deno.py` L37-40](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/deno.py#L37-L40) and `nodes/YtDlp/download.ts` L270-281, where `createWorkspacePlan` emits `--no-js-runtimes`, `--js-runtimes deno:<path>`, `--no-remote-components`. ADR 0011's prose ("yt-dlp'yi `--no-prompt --no-remote --no-config` ile başlatıyor"), which issue #99 restates, describes the Deno-level flags as if the node set them; it does not.

2. **Kanıtlanmış platform gerçeği:** `--remote-components` gates exactly two named components, and the default is empty. `--remote-components` takes a list, `default=[]`; `--no-remote-components` sets it to the empty list. The supported values registered at startup are `ejs:github` and `ejs:npm`, validated against `supported_remote_components`. Sources: [`options.py` L481-500](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/options.py#L481-L500), [`__init__.py` L1105-1106](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/__init__.py#L1105-L1106), [`globals.py` L40-41](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/globals.py#L40-L41).

3. **Kanıtlanmış platform gerçeği:** WHAT gets downloaded and FROM WHERE. `ejs:github` makes yt-dlp fetch `https://github.com/yt-dlp/ejs/releases/download/{_SCRIPT_VERSION}/yt.solver.{lib,core}.min.js` over yt-dlp's own HTTP stack and store it in the `challenge-solver` cache section. `ejs:npm` is not a yt-dlp download at all: it permits the Deno runtime to resolve the `npm:meriyah@6.1.4` and `npm:astring@1.9.0` specifiers that the vendored `yt.solver.deno.lib.js` imports. Sources: [`ejs.py` L291-305](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L291-L305), [`vendor/yt.solver.deno.lib.js`](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/vendor/yt.solver.deno.lib.js), [`deno.py` L48-63](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/deno.py#L48-L63).

4. **Kanıtlanmış platform gerçeği:** The remote fetch is version-pinned to the running yt-dlp, hash-verified, and therefore cannot deliver a *newer* solver. `_SCRIPT_VERSION = vendor.VERSION` is generated into yt-dlp's own source tree, the GitHub URL is built from that same constant, and outside developer mode any script whose major/minor differs from `_SCRIPT_VERSION` is rejected and any cached copy cleared, then the SHA3-512 of the code is compared against `vendor.HASHES`. Sources: [`ejs.py` L81-94](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L81-L94), [`ejs.py` L226-247](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L226-L247), [`vendor/_info.py`](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/vendor/_info.py). Enabling `ejs:github` is an *alternative delivery path for the same pinned version*, not an update channel; the EJS wiki's phrase "allow automatic updates" describes following yt-dlp's own pin without a separate reinstall, not overtaking it.

5. **Kanıtlanmış platform gerçeği:** The distribution the node ships already carries the solver locally, so `--no-remote-components` removes nothing from it. Script sources are consulted in order `python package → cache → vendored builtin → web`, and official PyInstaller executables bundle `yt-dlp-ejs`. `bundle/requirements/linux.txt` pins `yt-dlp-ejs==0.8.0`, and `bundle/docker/compose.yml` sets `REQUIREMENTS: linux` for the `musllinux_1_2_x86_64` service that produces `yt-dlp_musllinux`. Verified directly against the shipped bytes: `strings packages/linux-x64/bin/yt-dlp.musl` (reporting version `2026.07.14.233956`) contains `yt_dlp_ejs/yt/solver/core.min.js`, `yt_dlp_ejs/yt/solver/lib.min.js`, and the `yt_dlp_ejs.yt.solver` module names. Sources: [`ejs.py` L259-289](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L259-L289), [`bundle/requirements/linux.txt` L469](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/bundle/requirements/linux.txt#L469), [`bundle/docker/compose.yml` L116-121](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/bundle/docker/compose.yml#L116-L121), and the [EJS wiki distribution table](https://github.com/yt-dlp/yt-dlp/wiki/EJS) ("Official PyInstaller-bundled executable … No additional action required. `yt-dlp-ejs` is bundled with these executables"). Upstream states the same in the option help text itself: "This option is currently not needed if you are using an official executable" ([`options.py` L490-492](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/options.py#L490-L492)).

6. **Kanıtlanmış platform gerçeği:** Findings 4 and 5 together mean the causal claim in issue #99 — that `--no-remote` blocks yt-dlp from downloading up-to-date challenge-solver components, and that this is what breaks the node between Platform Package releases — is **not supported by the source**. For this distribution the flag the node actually sets (`--no-remote-components`) suppresses a fetch that (a) would never be reached because the python-package source wins first, and (b) would deliver byte-identical, hash-pinned code of the same version if it were reached.

7. **Kanıtlanmış platform gerçeği:** Direction 1 of the issue — pinning the challenge components into the Platform Package with exact tag/commit, asset name, SHA-256 and license — is already implemented in this repository. `packages/linux-x64/TOOLCHAIN.lock.json` carries a `yt-dlp-ejs` component with `upstream.repository: yt-dlp/ejs`, `tag: 0.8.0`, `commit: 4fb477f4af56880cfd324c48bd4294a2d2294e50`, assets `yt.solver.core.js` (`ca259e4e…`) and `yt.solver.lib.js` (`770831df…`), `license: "Unlicense AND MIT AND ISC"`, and source bundle `yt_dlp_ejs-0.8.0.tar.gz` (`d5fa1639…`). The files exist at `packages/linux-x64/assets/ejs/`, are listed in `execution-manifest.json` as `ejsCore`/`ejsLib`, are exposed on `VerifiedToolchain` by `packages/platform-selector/index.js`, and are licence-mapped in `packages/linux-x64/LICENSES.md`. Their upstream identity is confirmed by the generated header of `yt.solver.lib.js`, which names meriyah `6.1.4` (ISC) and astring `1.9.0` (MIT) as bundled dependencies under `SPDX-License-Identifier: Unlicense`.

8. **Kanıtlanmış platform gerçeği:** Those packaged assets are not delivered to yt-dlp at runtime, and yt-dlp exposes no mechanism to deliver them. `nodes/YtDlp/download.ts` never references `ejsCore`/`ejsLib`; the only consumer is the release gate (`test/platform-packages.test.ts`, the `official-ejs` job in `.github/workflows/publish.yml`), which runs the packaged solver under packaged Deno with `--no-remote --cached-only` and an empty `DENO_DIR` against frozen N/SIG vectors. On the yt-dlp side the local sources are the installed `yt_dlp_ejs` python package, yt-dlp's own cache directory, and the vendored copy inside yt-dlp — there is no CLI option that points the provider at an arbitrary local script file ([`ejs.py` L259-305](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L259-L305)). The packaged assets therefore function as independent release evidence that this exact solver works on this exact Deno, not as a runtime override.

9. **Kanıtlanmış platform gerçeği:** A locally cached module set *can* satisfy the Deno provider while `--no-remote` remains set, and yt-dlp already implements exactly that. Deno documents `--no-remote` as "Do not resolve remote modules", governs npm separately with `--no-npm` ("Do not resolve npm modules"), documents `--cached-only` as "Require that remote dependencies are already cached", and documents `--node-modules-dir=none` as "do not use a local node_modules directory; resolve npm packages from the global cache" ([`deno run` reference](https://docs.deno.com/runtime/reference/cli/run/), rolling docs accessed 2026-08-21). yt-dlp's `_npm_packages_cached` probes with `[*_DENO_BASE_OPTIONS, '--cached-only']` — `--no-remote` still present — and, when the probe succeeds, runs the `DENO_NPM` lib variant without `ejs:npm` being allowed ([`deno.py` L58-87](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/deno.py#L58-L87)). The supported local mechanism is therefore a pre-populated `DENO_DIR` global cache, not a `vendor/` directory; `https://docs.deno.com/runtime/reference/vendoring/` returned HTTP 404 on 2026-08-21, so no vendoring page was cited.

10. **Kanıtlanmış platform gerçeği:** The observed solver rotation cadence does not match the issue's premise, and the packaged solver is not stale today. `yt-dlp/ejs` has published eleven releases: `0.1.0` 2025-10-21, `0.2.0` 2025-10-23, `0.2.1` 2025-10-24, `0.3.0` 2025-10-29, `0.3.1` 2025-11-07, `0.3.2` 2025-12-07, `0.4.0` 2026-01-29, `0.5.0` 2026-02-21, `0.6.0` 2026-03-13, `0.7.0` 2026-03-13, `0.8.0` 2026-03-17 — and `0.8.0` is still the newest as of 2026-08-21 (source: `gh api repos/yt-dlp/ejs/releases`, [releases page](https://github.com/yt-dlp/ejs/releases)). yt-dlp's Changelog records the corresponding pins under release headings `2025.12.08` ("Update ejs to 0.3.2"), `2026.01.29` (`0.4.0`), `2026.02.21` (`0.5.0`), `2026.03.13` (`0.7.0`), `2026.03.17` (`0.8.0`), with no ejs bump in the three stable releases since ([`Changelog.md`](https://github.com/yt-dlp/yt-dlp/blob/2026.08.19/Changelog.md)). `vendor/_info.py` reports `VERSION = '0.8.0'` identically at tag `2026.06.09`, at the packaged nightly commit `aefce1ee`, and at current stable `2026.08.19`. The pattern is a burst of rotation in the first five months after EJS was introduced, then five months of stability — one rotation window, not a steady drumbeat.

11. **Kanıtlanmış platform gerçeği:** yt-dlp deliberately tolerates patch-level drift but not minor drift: the Changelog entry "Allow `ejs` patch version to differ" under release heading `2025.12.08` corresponds to the `version_tuple(...)[:2]` comparison in `_get_script`, so a `0.8.x` solver would be accepted against a `0.8.0` pin while a `0.9.0` one would be rejected with the warning "Challenge solver … script version … is not supported" ([`ejs.py` L226-235](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L226-L235)). Any local-component pinning scheme must respect that window; pinning a solver yt-dlp does not accept produces a hard provider rejection rather than a degraded solve.

12. **Kanıtlanmış platform gerçeği:** Staleness is **not** distinguishable as its own failure today; it falls through as a generic yt-dlp failure. The node's terminal error-code union in `nodes/YtDlp/process.ts` is `INVALID_SOURCE_URL | INVALID_ARGUMENTS | INVALID_ARTIFACT_SET | BINARY_TRANSFER_FAILED | PROCESS_OUTPUT_LIMIT | RESOURCE_LIMIT | REQUEST_TIMEOUT | YTDLP_FAILED`, and every non-zero yt-dlp exit becomes `YTDLP_FAILED` with the operator-facing message "yt-dlp could not complete the Download Request." (`nodes/YtDlp/YtDlp.node.ts` L79-85). ADR 0031 forbids logging stdout/stderr, extractor names, and argv, so the upstream discriminators never reach the operator. Upstream does emit discriminating text — `_director.__report_skipped_components` warns "Remote component … was skipped. It may be required to solve JS challenges" with a wiki link, `_get_script` raises "No usable challenge solver {type} script available", and a successful resolve logs "Using challenge solver … script v… (source: python package…)" at debug level ([`_director.py` L154-195](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_director.py#L154-L195), [`ejs.py` L245-255](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/ejs.py#L245-L255)) — but it reaches only yt-dlp's stderr, which the node discards. Note also that `__report_skipped_components` fires only when a provider actually rejects the request, so a working install never produces it.

13. **Lisans/güvenlik riski:** The security framing in the issue is directionally right but overstated in one respect and understates a different risk. `ejs:github` downloads are not unverified: the fetched script is rejected unless its SHA3-512 matches the hash baked into the running yt-dlp binary (finding 4), so that path is closer to "hash-pinned mirror" than "unsigned code download". `ejs:npm` is the materially riskier of the two, because yt-dlp launches Deno with `--no-lock` ([`deno.py` L37-40](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/yt_dlp/extractor/youtube/jsc/_builtin/deno.py#L37-L40)), which Deno documents as "Disable auto discovery of the lock file" ([`deno run` reference](https://docs.deno.com/runtime/reference/cli/run/)), so npm registry content would be resolved with no lockfile integrity check under the node's control. Either option would also require granting the Deno/yt-dlp process network egress and a writable cache location, both of which ADR 0013's `runtimeDownloads: false` policy and the `hermetic` release gate currently exclude.

14. **E2E ile doğrulanacak varsayım:** It is proven that the `yt_dlp_ejs` solver files are *inside* the packaged `yt-dlp.musl` bytes; it is **not** proven that `_pypackage_source` is the source actually selected at runtime inside the exact supported n8n image under the node's exact argv. The distinguishing evidence exists and is cheap to capture: with `--verbose`, a successful resolve prints `Using challenge solver lib script v0.8.0 (source: python package, variant: minified)`. Acceptance should assert that line (source `python package`, version equal to the Toolchain Lock `yt-dlp-ejs` tag) and assert the absence of any "Remote component … was skipped" or "No usable challenge solver" line, in the same lane that already runs `official-ejs` and `live-canary`. Until that runs, the claim "the node never needs remote components" is **doğrulanmadı** for the shipped image.

15. **E2E ile doğrulanacak varsayım:** It is not established that yt-dlp will keep bundling `yt-dlp-ejs` in official executables. The bundling is a property of `bundle/requirements/*.txt` and the PyInstaller build, not a documented compatibility guarantee; `pyproject.toml` lists `yt-dlp-ejs==0.8.0` in the `default` and `curl-cffi` dependency groups ([L58, L80](https://github.com/yt-dlp/yt-dlp/blob/aefce1eea4d0b6bab1ec2bd3beff09bff91a39c8/pyproject.toml#L58)), which is a version pin an upstream release can move at any time. A Toolchain Lock advance that silently loses the bundled solver would convert this from a non-issue into a hard `YTDLP_FAILED` at first challenge. A release-gate assertion that the candidate executable still contains `yt_dlp_ejs/yt/solver/*.min.js` (or the `--verbose` source line from finding 14) is the cheap guard.

16. **Ürün kararı:** The findings above relocate the risk but do not choose a lane, and the choice belongs to a human. What the evidence supports: direction 1 as literally written (pin the remote components locally) is already done and buys nothing further at runtime, because the components are already local via the official executable and yt-dlp offers no local-file override. The residual staleness window is the **yt-dlp version pin itself** under ADR 0013, which is direction 2 — but "the solver is stale between releases" is the wrong description of it, since the solver has not rotated since 2026-03-17 while yt-dlp shipped three stable releases in that period; extractor changes, not solver rotation, are what those releases carried. Direction 3 is the only one where a verified gap exists today (finding 12): a staleness or challenge-provider failure is indistinguishable from any other yt-dlp failure at the ADR 0031 boundary. Whether to spend on a discriminating outcome code, on release cadence, or on neither, is a product decision to be taken by a human.

17. **Cevapsız soru:** The historical split between "site broke because the EJS solver rotated" and "site broke because an extractor changed" is not derivable from the sources inspected here. The yt-dlp Changelog groups extractor fixes and ejs bumps under the same release headings without linking a breakage to its cause, and `yt-dlp/ejs` release notes were not inspected per-release. Without that split, the expected cost of any given release cadence remains **doğrulanmadı**.
