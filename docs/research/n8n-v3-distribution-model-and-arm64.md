## Search surface

For the "v3 is Docker-only" premise the following first-party surfaces were searched:
docs.n8n.io live pages and the `n8n-io/n8n-docs` tree at the pinned commit (1474 Markdown
files, path and full-text search); `n8n-io/n8n` GitHub releases, git tags and branches; the
npm registry metadata for the `n8n` package; and n8n's own community forum Announcements
category. A first-party source **was** found (findings 1–3). What was *not* found is recorded
in finding 9: the claim is carried by n8n's documentation and its own forum, not by any GitHub
release note, changelog entry for a shipped version, or npm deprecation marker.

This note deliberately does not restate the install-gate, Community Packages installer, or
`os`/`cpu` metadata findings — those live in `platform-support-and-install-gates.md` and are
unchanged. This note only adds the v3 distribution premise and the architecture evidence.

## Findings

1. **Kanıtlanmış platform gerçeği:** A first-party n8n source for the Docker-only premise exists and is unambiguous. n8n's own breaking-changes page for 3.0 states that self-hosted n8n will require a Docker-based deployment and that installations run via `npm` / `npx n8n` will no longer be supported. Sources: [`v30-breaking-changes.md#L21`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/changelog/v30-breaking-changes.md#L21) and the live page [docs.n8n.io/changelog/v30-breaking-changes](https://docs.n8n.io/changelog/v30-breaking-changes) (HTTP 200 at access time).

2. **Kanıtlanmış platform gerçeği:** The same first-party page dates the transition: n8n 3.0 is described as scheduled for October 2026, and the migration instruction is to move off `npm`/`npx` before upgrading, with Docker Compose named as the expected easiest local path. Sources: [`v30-breaking-changes.md#L13`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/changelog/v30-breaking-changes.md#L13) and [`#L22`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/changelog/v30-breaking-changes.md#L22).

3. **Kanıtlanmış platform gerçeği:** The premise is corroborated by three further independent first-party docs pages, so it is not a single stray sentence: the npm install page carries a feature-availability warning that npm-based installs are deprecated from n8n 3.0; the one-line-setup page states that from v3 n8n is only distributed through Docker while existing npm installs keep working for now; and the hosting index page marks the npm method as being deprecated in n8n 3.0. Sources: [`install-with-npm.md#L15`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/deploy/host-n8n/install-options/install-with-npm.md#L15), [`one-line-setup.md#L17`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/deploy/host-n8n/install-options/one-line-setup.md#L17), [`host-n8n/README.md#L98`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/deploy/host-n8n/README.md#L98).

4. **Kanıtlanmış platform gerçeği:** The decision has a first-party provenance trail predating the docs. n8n posted a consultation in the Announcements category of its own community forum on 2026-06-10 proposing to sunset npm-native support, motivated by an embedded AI assistant needing a sandbox. It is a proposal, not the decision, and it names no version and no CPU architecture. Source: [community.n8n.io announcement thread](https://community.n8n.io/t/your-view-on-a-proposed-change-requiring-docker-to-run-n8n/298916).

5. **Kanıtlanmış platform gerçeği:** Docker-only does not mean x64-only, and no first-party n8n artifact says otherwise. The 3.0 breaking-changes page names no CPU architecture anywhere in its Deployment section or elsewhere, and the Docker install page states no architecture requirement or restriction. Sources: [`v30-breaking-changes.md`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/changelog/v30-breaking-changes.md) and [`install-with-docker.md`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/deploy/host-n8n/install-options/install-with-docker.md).

6. **Kanıtlanmış platform gerçeği:** The official n8n image is a multi-architecture OCI index carrying both `linux/amd64` and `linux/arm64`, at `latest` and at every 2.x anchor this repository pins. Registry inspection of `n8nio/n8n` returned `application/vnd.oci.image.index.v1+json` with exactly four descriptors per tag — one `linux/amd64` image manifest, one `linux/arm64` image manifest, and two `unknown/unknown` attestation manifests referencing them — for `latest`, `2.0.0`, `2.27.4`, and `2.34.5`. The 2.34.5 amd64 platform digest `sha256:7e82936b…` and index digest `sha256:d91033b4…` match the values already recorded in [`n8n-2x-release-gate-matrix.md`](./n8n-2x-release-gate-matrix.md), which cross-validates the read. Sources: registry manifests listed under Version anchors, read from `docker.n8n.io/n8nio/n8n` and Docker Hub `n8nio/n8n` on 2026-08-21.

7. **Kanıtlanmış platform gerçeği:** arm64 is a declared, deliberate output of n8n's release build, not an accident. The Docker build/push workflow takes its matrix from `docker-config.mjs`, whose build context defaults to `platforms: ['linux/amd64', 'linux/arm64']`; that default is what versioned/stable, `release`, `workflow_call`, and nightly `schedule` builds use. Only dev builds — `pull_request`, `workflow_dispatch`, and pushes to non-`master` branches — narrow the list to `['linux/amd64']`. Each platform gets its own runner (`blacksmith-8vcpu-ubuntu-2204-arm` for arm64) and the per-arch images are joined into a manifest afterwards. Sources: [`docker-config.mjs#L14`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/.github/scripts/docker/docker-config.mjs#L14), [`#L30-L60`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/.github/scripts/docker/docker-config.mjs#L30-L60), [`#L89-L110`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/.github/scripts/docker/docker-config.mjs#L89-L110), and [`docker-build-push.yml#L94-L100`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/.github/workflows/docker-build-push.yml#L94-L100) / [`#L171`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/.github/workflows/docker-build-push.yml#L171), n8n 2.34.5.

8. **Kanıtlanmış platform gerçeği:** The whole base-image chain supports arm64, so nothing below n8n constrains the architecture. The runtime image is `FROM n8nio/base:24.18.0@sha256:29d9c11f…`, and `n8nio/base:24.18.0` is itself a multi-arch OCI index containing `linux/amd64` and `linux/arm64`. That base is built `FROM dhi.io/node:24.18.0-alpine3.24-dev@sha256:d5084532…`, a Docker Hardened Image of Node 24 on Alpine 3.24. Sources: [`docker/images/n8n/Dockerfile#L32`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/docker/images/n8n/Dockerfile#L32), [`docker/images/n8n-base/Dockerfile#L4`](https://github.com/n8n-io/n8n/blob/f745babb4b5a72bdecf454f2cc81f0ba7d9c0e19/docker/images/n8n-base/Dockerfile#L4), and the `n8nio/base:24.18.0` index digest listed under Version anchors.

9. **Kanıtlanmış platform gerçeği:** v3 is announced but not released, and this is the exact boundary of what the primary sources support. As of the access date there is no `n8n@3.*` git tag, no 3.x GitHub release, and no 3.x version on npm; the newest stable release is `n8n@2.35.7` (published 2026-08-21) and npm dist-tags are `latest`/`stable` = `2.35.7`, `next`/`rc`/`beta` = `2.36.5`. The `n8n` npm package itself carries no deprecation marker on any 2.x version. The Docker-only claim therefore has a first-party source, but it is a forward-looking documentation commitment, not a shipped change. Sources: [n8n releases](https://github.com/n8n-io/n8n/releases), [npm `n8n` registry metadata](https://registry.npmjs.org/n8n).

10. **Kanıtlanmış platform gerçeği:** v3 pre-release artifacts already exist and are dual-architecture. Docker Hub `n8nio/n8n` carries `v3-rc-20260811.1`, `v3-rc-20260817`, and `v3-rc-20260817.1`; each resolves to an OCI index with both `linux/amd64` and `linux/arm64`. The arm64 manifest of `v3-rc-20260817.1` is a real, complete image — 12 layers totalling about 347 MiB — whose config blob reports `architecture: arm64`, `os: linux`, `org.opencontainers.image.version = v3-nightly`, `org.opencontainers.image.source = https://github.com/n8n-io/n8n`, and `NODE_VERSION=24.18.1-r0` on `dhi/node` `24.18.1-alpine3.24-dev`. Source: registry read of `n8nio/n8n` tag list and of manifest `sha256:a198ffca…` plus its config blob, 2026-08-21.

11. **Kanıtlanmış platform gerçeği:** The v3 line's own source keeps the dual-platform default. On the `3.x` branch, `docker-config.mjs` still declares `platforms: ['linux/amd64', 'linux/arm64']` as the build-context default; the only edit versus 2.34.5 is that manual `workflow_dispatch` builds can now *opt into* arm64 via an `includeArm64` flag, commented as a pre-merge proof path for native-binary checks. That is a widening of arm64 coverage, not a narrowing. Source: [`3.x docker-config.mjs#L14`](https://github.com/n8n-io/n8n/blob/670e4c423fb42f1da45bcc1077ee7ae19da042af/.github/scripts/docker/docker-config.mjs#L14) and [`#L36-L44`](https://github.com/n8n-io/n8n/blob/670e4c423fb42f1da45bcc1077ee7ae19da042af/.github/scripts/docker/docker-config.mjs#L36-L44).

12. **Kanıtlanmış platform gerçeği:** n8n has a first-party precedent that matches this package's shape almost exactly, and it treats arm64 as in-scope while treating npm and custom images as out-of-scope. For the Kafka node's version 2 preview, which "includes a native compiled component", n8n documents that it has verified the preview "on the official n8n Docker images, on both amd64 and arm64", and that "other install methods, such as npm or custom images, aren't verified during the preview". Sources: [`n8n-nodes-base.kafka.md#L53`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/integrations/builtin/app-nodes/n8n-nodes-base.kafka.md#L53) and [`n8n-nodes-base.kafkatrigger.md#L62`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/integrations/builtin/trigger-nodes/n8n-nodes-base.kafkatrigger.md#L62).

13. **Kanıtlanmış platform gerçeği:** No first-party artifact makes community-node or custom-extension support differ by architecture. Full-text search of the pinned n8n-docs tree returns `arm64` on exactly two pages — the two Kafka pages in finding 12 — and neither the community-nodes installation, management, nor troubleshooting pages state any architecture condition. Source: code search over [`n8n-io/n8n-docs@cc3d4ce1`](https://github.com/n8n-io/n8n-docs/tree/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/integrations/community-nodes).

14. **Kanıtlanmış platform gerçeği:** The Community Packages module still exists on the `3.x` branch at `packages/cli/src/modules/community-packages/community-packages.service.ts`, so v3 as currently staged does not remove the install path this package depends on. Source: [`3.x community-packages.service.ts`](https://github.com/n8n-io/n8n/blob/670e4c423fb42f1da45bcc1077ee7ae19da042af/packages/cli/src/modules/community-packages/community-packages.service.ts).

15. **Kanıtlanmış platform gerçeği:** None of the documented v3 breaking changes touches this package's surface. The published list is: removal of the legacy Function, Function Item and Item Lists nodes; removal of older Execute Workflow behavior; removal of version 1 of the AI Agent node and its SQL/Conversational/OpenAI Functions/Plan-and-Execute/ReAct modes; removal of the `$getPairedItem` expression helper; stronger security defaults; and retirement of Chat hub, editor workflow-import-from-URL, and non-functional nodes. This package ships none of those, and ADR 0027 already keeps it out of the AI Agent tool surface for v0.2.0. Source: [`v30-breaking-changes.md#L25-L66`](https://github.com/n8n-io/n8n-docs/blob/cc3d4ce1e33f7bc7b6a8c7e51806012568977f5e/docs/changelog/v30-breaking-changes.md#L25-L66).

16. **Ürün kararı:** Nothing in this release stops or changes. ADR 0007, ADR 0028, and `README.md:35` already scope Doğrulanmış Destek to the official n8n Docker image; a first-party move that makes Docker the only self-hosted distribution narrows the world *toward* this repository's existing premise rather than away from it. The two-tier n8n compatibility statement of ADR 0008 and the three-anchor 2.x release gate of ADR 0025 are untouched, because v3 is unreleased (finding 9).

17. **Ürün kararı:** ADR 0007's factual premise is now verified rather than assumed. Its wording already concedes that official n8n and yt-dlp arm64 artifacts exist and rests the arm64 exclusion on missing native E2E, not on missing upstream builds. Findings 6, 7, 8, 10 and 11 confirm the conceded half is true at every anchor and on the v3 line. The ADR's arm64 clause therefore needs no correction; what it needs, if arm64 is ever added, is the E2E it names — and the correct reading of "Docker-only" is that it removes the npm host tier, not the arm64 architecture tier.

18. **Lisans/güvenlik riski:** Publishing an arm64 platform package is not a metadata edit. It duplicates the entire component-license surface of ADR 0024 and ADR 0012 on a second architecture — a second pinned GPL FFmpeg/FFprobe build with its own corresponding-source bundle, a second yt-dlp and Deno artifact set, and a second attestation manifest under ADR 0029. Upstream image availability says nothing about whether those arm64 artifacts exist under the same licence terms, at the same pinned versions, with the same digests recorded.

19. **E2E ile doğrulanacak varsayım:** Because the official image's arm64 variant is now proven to exist and to be a complete image, an arm64 release is gated only by execution evidence. Adding it must repeat the full ADR 0025 anchor sweep against the arm64 *platform* manifests (for 2.34.5 that is `sha256:ce017981…`), on native arm64 hardware, proving Community Packages install, queue-worker load, yt-dlp/FFmpeg/FFprobe execution, and source-bundle integrity. Running an arm64 image under emulation on an x64 host proves nothing about the packaged binaries and must not be accepted as this evidence.

20. **E2E ile doğrulanacak varsayım:** If and when a 3.x image is published, the release gate must be re-cut against it before any v3 support claim. ADR 0008's two-tier compatibility statement currently excludes 3.x, and finding 14 (module still present on a moving branch head) is a snapshot of unreleased code, not a compatibility guarantee.

21. **Cevapsız soru:** Whether n8n 3.0 changes anything about community-package installation, the `~/.n8n/nodes` layout, or npm-sourced community nodes is **doğrulanmadı**. The breaking-changes page closes by saying it "will be updated with full details, migration guides, and links as n8n 3.0 approaches its release", so its silence on community nodes today is not a commitment. The page must be re-read before v3 is treated as compatible.

22. **Cevapsız soru:** The promised npm-to-Docker migration guide does not exist yet — both the breaking-changes page and the one-line-setup page say step-by-step guidance is "coming soon". Whether that guide will state a supported architecture matrix, and whether it will address community nodes installed under an npm deployment, is unknown.

23. **Cevapsız soru:** Whether n8n will ever publish an official statement scoping v3 support by CPU architecture is unknown. The current evidence is entirely behavioural — manifests and build workflows — with no prose commitment from n8n that arm64 is a *supported* target rather than merely a *built* one. This repository should not infer an upstream support promise from the presence of an arm64 manifest.
